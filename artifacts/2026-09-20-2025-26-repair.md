## TL;DR

The exclusion is **case (i)** — a workaround for a page that did not exist, not a deliberate
suppression of known-bad data. Commit **`0459cdc`** (2025-12-11 22:23:22, Aaryn Olsson),
message: *"Fix Top 10 by Year dropdown - exclude 2025-26 (no page exists yet)"*.

**But the remedy that case (i) implies is not available.** The repo does not contain the data
needed to build `records/top10-{boys,girls}-2025-26.md`. Committed content yields **19 of the
~97 rows** such a pair of files needs, and **11 of those 19 have no date and no meet**. A
top-10 built from that would not be an incomplete list; it would be a *wrong* one — it would
show one swimmer in the 50 Free for a season that had 30 swimmers and 269 swims.

So I did **not** remove the exclusion's effect and did **not** add any 2025-26 Top-10 nav link.
Per the dispatch: a nav link to a page I did not build is worse than the current state.

What I did instead is narrow and provably output-neutral: replaced the **hardcoded-by-name**
exclusion with a **filesystem-derived** one, so the menu lists exactly the seasons whose
top-10 sources exist. Today that is byte-identical to current behaviour; in future it
self-corrects instead of needing another hand edit.

## 1. Why the exclusion exists

```
$ git log -S "2025-26" --oneline -- scripts/generate_annual_pages.py
c6805ba Reorganize scripts into scripts/ directory      # path move only

$ git blame -L 29,30 scripts/generate_annual_pages.py
0459cdcc (Aaryn Olsson 2025-12-11 22:23:22 -0700 29) # Seasons that have top10 pages (excludes current season)
0459cdcc (Aaryn Olsson 2025-12-11 22:23:22 -0700 30) TOP10_SEASONS = [s for s in SEASONS if s != "2025-26"]
```

`0459cdc` is titled **"Fix Top 10 by Year dropdown - exclude 2025-26 (no page exists yet)"**.
Its diff does one thing: swap `SEASONS` for `TOP10_SEASONS` in the dropdown comprehension, and
drop the resulting dead `<li>` from 13 already-generated annual pages.

The word *"yet"*, and the fact that the commit removes a **link** rather than any **content**,
settle it. This is **(i) a workaround for a missing page**. It is not (ii): nothing in the
commit, its message, or the surrounding history says 2025-26 data is knowingly untrustworthy.

Corroborating evidence that 2025-26 is *trusted*, not suppressed: the season's annual summary
is fully wired and live — `generate_annual_pages.py:19-23` includes `"2025-26"` in `SEASONS`,
`docs/annual/2025-26.html` is generated, and it is linked from the "Summary by Year" menu
(`generate_website.py` literal) **and** from `docs/index.html:80,307,330`. Only the Top-10
half is missing, and only because its source files were never produced.

## 2. What I could NOT build, and why

### The data is not in the repo

A season top-10 is a **ranked field**: every swimmer's season-best per event, ordered. The
generator that produces it (`generate_all_season_top10.py`) reads `data/raw/swimmers/*.csv`,
which is gitignored (`.gitignore:30`) and absent from both the sandbox and the upstream
checkout. That is the root cause, and it is the importer worker's subject, not mine.

I checked every committed artefact that carries 2025-26 swims, using the season boundary
stated by code (`generate_all_season_top10.py:35-38`: `YYYY-YY` = `[YYYY-08-01, YYYY+1-08-01)`):

| Source | What it holds for 2025-26 | Usable for a top-10? |
|---|---|---|
| `records/annual-summary-2025-26.md` → "Season Best Times" | 8 events x 2 genders, **rank 1 only**, and the table has **no Date and no Meet column** | rank 1 only, undated |
| `records/annual-summary-2025-26.md` → "Records Broken" | 4 entries (already a subset of the above) | no new rows |
| `records/annual-summary-2025-26.md` → "Active Swimmers" | 30 swimmers with **swim counts, no times** | no |
| `data/class_records_history.json` | 10 entries (7 boys, 3 girls) — **class records only** | adds a few dated rows |
| `records/records-{boys,girls}.md` | 12 rows dated in-season (8 distinct after removing Open duplicates) | same rows as above |
| `data/historical_splits/splits_25-26.json` | relay splits — **no total time, no date, no meet**; and season top-10 files are individual-only | no |
| `data/records/` (stale fork) | no `top10-*-2025-26.md` either | no |

is a worse outcome than the honest absence that exists today.

**Conclusion: `records/top10-{boys,girls}-2025-26.md` cannot be derived from committed content.
Recorded as the gap. I did not fabricate, reconstruct or scrape anything to close it.**

## 3. What I did build

### 3a. `scripts/generate_annual_pages.py` — exclusion is now derived, not hardcoded

The old line excluded the string `"2025-26"`. That is a latent trap: when 2026-27 is added to
`SEASONS`, 2025-26 stays excluded **forever** even once its files appear, and 2026-27 is
immediately linked to a page that does not exist — reintroducing the exact bug `0459cdc` fixed.

Replaced with a test of what actually exists on disk. Both genders are required, because the
menu links the boys page and the gender toggle rewrites the same href to the girls page — so
a boys-only file would still 404 for half the site.

### 3b. `scripts/generate_website.py` — same list, same source

The "Top 10 by Year" menu existed as a **hand-written 18-line HTML literal** at `:53-70`,
a third copy of the same season list. It is now derived from the same helper, so the two
generated navs cannot drift apart.

`docs/index.html` holds a fourth, hand-maintained copy (`:57-74`). I left it untouched — it
already ends at 2024-25, which is correct, and there is nothing to add to it.

### 3c. `scripts/validate_records.py` — new stdlib linter (the survey's proposal)

No dependencies, no network, never rewrites a file. Checks rank contiguity, `(time, date,
participants)` uniqueness, monotonic times down the ranks, known/non-repeated grade labels,
date and time parseability, and that each event's bold **Open** row equals the fastest grade
row in that event.

It understands the formats the hand-maintained files actually use: `22.43r` (relay leadoff),
`Nov 2007` and `2013-14` (coarse dates where the exact meet date was never recovered), and
all-em-dash placeholder rows (deliberate "no swim recorded this season" markers).

```
$ python3 scripts/validate_records.py
validate_records: 3 problem(s) across 272 tables
```

All three are pre-existing, all outside 2025-26, **none touched** — see Open Questions.
The Open-vs-fastest-grade check passes on every event in both files, which is independent
confirmation that the December 2025 hand corrections left `records/*.md` self-consistent.

```

patched  (this branch):       run1 vs run2  -> byte-identical
```

### Output-neutrality — the patch renders nothing new

```
diff -r docs.BASE1 docs.AFTER1   ->  no output
```

The full `docs/` tree rendered from unmodified `HEAD` and from this branch are **byte-identical**.
Both derivations produce the same 18 seasons, in the same order:
`2007-08 … 2024-25`.

### The known benign churn — and why this PR does not carry it

Re-rendering on any date after 2025-12-16 rewrites two lines in each of **55 files**:

```
<     <p class="mb-2">&copy; 2025 Tanque Verde High School Swimming</p>
>     <p class="mb-2">&copy; 2026 Tanque Verde High School Swimming</p>
<                 Generated on December 16, 2025 |
>                 Generated on September 20, 2026 |
```

That is the *only* difference between committed `docs/` and a fresh render of `HEAD` — content
is unchanged. **Because this PR's code change is provably output-neutral, I deliberately did
not commit a regenerated `docs/`.** Committing it would add 55 files of pure date churn with
zero content value and would restamp the live site's "Generated on" date for a change that
alters nothing a visitor sees. Whoever next regenerates for a real content change will pick
the churn up then; it should not be mistaken for content movement.
