# Tanque Verde Swim — importer assessment

**PRIMARY FINDING: (C) BROKEN INTEGRATION.** The `swim-data-tool` record-generator seam is broken by a data-contract migration: the dependency moved from a CSV file contract (v0.9.0) to a PostgreSQL one (v0.13.0), and this repo's five generator scripts were never updated. Both sides exist and are alive.

**SECONDARY (A) MISSING SETUP/DATA:** the in-repo standalone harvesters are *not* broken — two of them acquire live data today and one reproduces committed output byte-identically. They needed only `pip install -r requirements.txt`.
**SECONDARY (B) MOVED DEPENDENCY:** `swim-data-tool` is alive on GitHub but exists nowhere on this machine, and both documented local paths are wrong.
**SECONDARY (C), different cause:** `parse_aia_state_meets.py` — AIA changed its published PDF format between 2023 and 2024.
**(D) GENUINELY UNAVAILABLE:** SwimCloud only (Cloudflare bot challenge).

**This report corrects the earlier survey's conclusion that the harvest/import pipeline is "dead on this machine."** That was too broad. The website-generation path was correctly assessed, but the harvest path was judged from absence rather than from execution. Run properly, most of it works.

## 2. The integration test — what actually breaks, and why

This repo imports exactly these symbols. **All four still exist and import cleanly at HEAD:**

```
OK    swim_data_tool.services.record_generator.RecordGenerator
OK    swim_data_tool.models.events.convert_time_to_seconds
OK    swim_data_tool.models.events.format_event_name
OK    swim_data_tool.sources.maxpreps.MaxPrepsSource
```

So the earlier survey's "`ModuleNotFoundError` on line 1" is a **provisioning** symptom, not an API break. Install fixes the import.

The break is one level deeper — in the **data contract**:

**v0.9.0** (`record_generator.py`), matching what this repo's scripts expect:
```python
def load_all_swimmer_data(self) -> pd.DataFrame:
    """Load all swimmer CSVs from raw directory."""
    if not self.raw_dir.exists():
        return pd.DataFrame()
    csv_files = list(self.raw_dir.glob("*.csv"))
```

**v0.13.0 / HEAD**, the same method:
```python
def load_all_swimmer_data(self) -> pd.DataFrame:
    """Load all swimmer data from database."""
    conn = self.db.get_connection()          # psycopg2.connect(...)
    query = f"SELECT ... FROM {main_schema}.swims swims INNER JOIN ..."
    df = pd.read_sql_query(query, conn)
```

CSV loading was demoted to a private `_load_from_csv()` that `load_all_swimmer_data()` **no longer calls**. `__init__` now unconditionally constructs a `RecordDatabase`, so the failure happens in the constructor, before any data is touched.

### One more packaging defect, worth knowing

`version.py` / `__init__.py` read `Path(__file__).parents[2] / "VERSION"`. From a source checkout that resolves to the repo root; from `site-packages` it resolves to `lib/python3.11/VERSION`, which does not exist:
```
FileNotFoundError: [Errno 2] No such file or directory: '/tmp/sdt-venv/lib/python3.11/VERSION'
```
So a plain `pip install` of swim-data-tool yields a **CLI that cannot start at all**. `uv run swim-data-tool` from the source checkout works fine (`swim-data-tool, version 0.13.0`, full 21-command help). That is why `test_season_ranges.sh` uses `uv run` — it is the only invocation that works, and it requires a local checkout.

### 3c. `parse_aia_state_meets.py` — acquisition fine, parser out of date

Downloads work, including with the script's own header-less `urlretrieve`:
```
2024: HTTP 200 bytes=494319 magic=b'%PDF-'    2023: HTTP 200 bytes=675854
2019: HTTP 200 bytes=1166836                  2012: HTTP 200 bytes=1055758
```
Parsing, though, depends on the year:

| Year | Regex matches (any school) | School rendered as | TV swims extracted |
|---|---|---|---|
| 2012 | 0 | `Tanque Verde` (3 lines) | 0 |
| 2019 | 254 | `Tanque Verde` (18 lines) | 0 |
| 2023 | 665 | `Tanque Verde` (33 lines) | **8** |
| 2024 | **0** | **`TVHS`** (58 lines) | 0 |

2023 works end to end:
```json
{"place": 11, "name": "Zachary Duerkop", "grade": 10, "school": "Tanque Verde High School",
 "prelim_time": "1:55.34", "finals_time": "1:54.85", "event": "200 Free", "gender": "M"}
```

2024 fails for two compounding reasons:
1. **The school name changed representation.** `parse_aia_pdf(school_name="Tanque Verde")` does a literal substring match. The 2024 PDF writes results rows as `TVHS` (58 occurrences); "Tanque Verde High School" survives only in 4 team-score lines.
2. **The row format changed.** `parse_swimmer_line`'s regex expects `place, "Last, First", 2-digit grade, full school name, prelim, finals`:
   `12 Olsson, Wade 09 Tanque Verde High School 5:24.27 5:17.84`
   The 2024 PDF emits `5 Duerkop, Zachary TVHS 54.45` — no grade, abbreviation, one time. Passing `school_name="TVHS"` still yields **0 swims**, confirming the regex itself no longer matches, not just the name.

Additionally the 2024 text extracts **column-interleaved** (`29.28 29.22 24.93 24.04 26 VALL A 2:06.47 20 Kowalski, Peyton TVHS 2:03.57`), so naive `extract_text().split('\n')` scrambles rows regardless of the regex. The 2019 result (254 generic matches but 0 TV swims) is likely the same layout problem plus the event-header state machine; **I did not isolate that one and am not claiming a cause.**

The registry already carries `{"year": 2025, "file_id": None}` — the 2025 PDF id was never resolved, so 2025 is not attempted at all.

## 4. What a repair would involve (describing only — nothing was changed)

**Cheapest path to a repeatable import, roughly in value order:**

1. **Provision the standalone harvesters.** `python3 -m venv .venv && pip install -r requirements.txt && playwright install chromium`. That alone restores `harvest_all_relay_splits.py` and `harvest_azpreps365_v3.py` to full function — proven above. No `swim-data-tool` involved. This is most of the usable ingest.
2. **Decide the swim-data-tool relationship deliberately.** Three options, materially different:
   - *Pin to v0.9.0* — `pip install git+https://github.com/aaryno/swim-data-tool.git@v0.9.0`. Smallest change; the five generators work unmodified against `data/raw/swimmers/*.csv`. Freezes this repo on a year-old dependency.
   - *Adopt v0.13.0* — requires standing up PostgreSQL, a `swim_data_tool` role, the schema, `.env`/`site-config.json`, `psycopg2-binary`, and **rewriting the five scripts** to the DB contract.
   - *Vendor the ~4 functions actually used* (`load_all_swimmer_data`, `filter_team_swims`, `parse_and_normalize_events`, plus `convert_time_to_seconds`/`format_event_name`) into this repo and drop the dependency. v0.9.0's CSV implementation is small. This matches what `claude.md` already claims the repo is — "largely independent" — and removes the seam permanently.
3. **Re-fit the AIA parser to the 2024+ format.** Needs school-abbreviation matching (`TVHS`) alongside full names, a regex for the no-grade/one-time row shape, and column-aware extraction (`page.extract_words()` with x-position bucketing, or `extract_table`) instead of `extract_text().split('\n')`. Also resolve the missing 2025 `file_id`.
4. **Fix the documented paths** — `README.md:193`, the `claude.md` relationship section, `run_season_update.py:66,73` — and either correct or delete `.swim-data-tool-version`, which names a nonexistent release.
5. **Upstream, if it is yours to change:** declare `psycopg2` as a dependency, and fix `version.py`'s `parents[2] / "VERSION"` so the package is installable at all.

**The `run_season_update.py` path-resolution bugs catalogued in the earlier survey were not re-verified here** — that script was out of scope for this assessment and I did not run it.
